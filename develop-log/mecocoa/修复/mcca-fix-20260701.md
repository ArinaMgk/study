## 死锁与重定向错乱 — 根因分析

经过对 [message.cpp](file:///her/mecocoa/mecocoa/message.cpp)、[fileman.cpp](file:///her/mecocoa/mecocoa/fileman.cpp)、[schedul.cpp](file:///her/mecocoa/mecocoa/schedul.cpp)、[syscall.cpp](file:///her/mecocoa/mecocoa/syscall.cpp)、[taskman.cpp](file:///her/mecocoa/mecocoa/taskman.cpp) 的完整审查，定位到 **三个独立的并发缺陷**，它们共同导致了你观察到的全部症状。

---

### 根因 1（主因）：`f_desc_table` 全局描述符表无锁竞争

这是「**a.txt 输出到 d.txt**」的直接原因，也是管道死锁的主要推手。

**事实**：[fileman.cpp:12](file:///her/mecocoa/mecocoa/fileman.cpp#L12) 定义了一个全局 `FileDescriptor f_desc_table[0x1000/sizeof(FileDescriptor)]`，被以下三条路径**同时**线性扫描空槽，且各自只持有**本进程的 fileman 锁**，没有任何全局锁保护这张表：

| 调用方 | 入口 | 持有的锁 | 扫描点 |
|---|---|---|---|
| `serv_file_loop` 处理 open | [fileman.cpp:51](file:///her/mecocoa/mecocoa/fileman.cpp#L51) | **被打开进程**的 fileman | `ProcessBlock::Open` |
| 用户线程直接调用 pipe | [fileman.cpp:350](file:///her/mecocoa/mecocoa/fileman.cpp#L350) | **当前进程**的 fileman | `ProcessBlock::Pipe`（`sysc_PIPE` 绕过 serv_file_loop） |
| 用户线程直接调用 dup2 | [fileman.cpp:384](file:///her/mecocoa/mecocoa/fileman.cpp#L384) | **当前进程**的 fileman | `FileDescriptor_Clone` |
| `serv_task_loop` 处理 fork | 同上 | **子进程**的 fileman | `CreateFork` 对每个 fd 调 `FileDescriptor_Clone` |

由于 fileman 锁是**每进程一把**（见 [taskman.hpp:321](file:///her/mecocoa/include/taskman.hpp#L321) `MutexBlock<ProcFiles> fileman`），上述四条路径运行在 4 个不同 CPU 上时**互不互斥**，但都在读写同一张全局表。

**竞争窗口**：
```
CPU0 (serv_file_loop, 为进程A打开 a.txt)        CPU1 (子进程B 正在 dup2)
  扫描到 f_desc_table[i].vfile == null           扫描到 f_desc_table[i].vfile == null
  pfd = &f_desc_table[i]                         pfd = &f_desc_table[i]
  *pfd = {a.txt, ...}   ← 先写                    *pfd = {d.txt, ...}  ← 后写，覆盖！
  files->pfiles[fd] = pfd                         files->pfiles[fd] = pfd
```
两个进程都认为自己占有了槽 `i`，但槽里只剩下**后写者**的数据。进程 A 的 `pfiles[fd]` 指向槽 `i`，读到的却是 `d.txt` —— 这就是「明明用的是 a.txt 但是输出 d.txt」的机制。

**对管道的破坏**：`FileDescriptor_Clone` 在 [fileman.cpp:396-407](file:///her/mecocoa/mecocoa/fileman.cpp#L396-L407) 里根据 `f_mode` 分别 `chan->reader_count++` / `chan->writer_count++`。一旦两个 clone 抢到同一槽：
- 被覆盖的那一侧**已经把 reader_count 或 writer_count 加过了**，但它持有的 `FileDescriptor` 实际指向另一侧的数据。
- 后续 close 时会按**错误的 f_mode** 递减计数 → `reader_count`/`writer_count` 永久错位。

后果直接命中你观察到的现象：
- `cat` 阻塞在 [filesys.cpp](file:///her/mecocoa/mecocoa/filesys.cpp) 的 `ReadPipe`：`chan->buffer.is_empty() && chan->writer_count != 0` → 永远不满足 EOF，`cat` 在 `rq` 上挂死。
- `ls` 的写端被覆盖成读端 → `WritePipe` 行为异常，或写端指向了另一个 pipe → 数据进了虚空。
- 管道两端的 refcount 一旦错位，`ls` 退出后 `writer_count` 不归零，`cat` 永远等不到 EOF。

这与 dump 完全吻合：TID 12 无名、`RECV=null(ANYPROC)`、`QHEAD=null` —— 正是 `ReadPipe` 里 `th->Block(BR_RecvMsg)` 的特征（不设 `recv_fo_whom`，不在任何 send 队列里）。TID 10、11 不在 `thchain` 中，说明它们要么已走完 `DestroyThread`（但 shell 未被唤醒，见根因 2），要么根本没成功创建。

---

### 根因 2：`Block()` 与 `Unblock()` 之间无锁窗口

[schedul.cpp:374-394](file:///her/mecocoa/mecocoa/schedul.cpp#L374-L394)：

```cpp
void ThreadBlock::Block(BlockReason reason) {
    Taskman::DequeueReady(this);          // 内部短暂获取再释放 scheduler_lock
    state = State::Pended;                 // ← 此刻不持锁
    block_reason = block_reason | reason;  // ← 此刻不持锁
}

void ThreadBlock::Unblock(BlockReason reason) {
    SpinlockLocal guard(&scheduler_lock); // 持锁
    block_reason = block_reason & ~reason;
    if (block_reason == BR_None) {
        state = State::Ready;
        Taskman::EnqueueReady(this, false);   // 入就绪队列
        WakeThreadOnRecordedCpu(this);        // 跨核 IPI 唤醒
    }
}
```

`Block()` 在 `DequeueReady` 返回后、设置 `state=Pended` 之前存在一个**无锁窗口**。若另一 CPU 在此窗口内调用 `Unblock()`（例如管道对端写入数据唤醒读端）：

1. `Unblock()` 持 `scheduler_lock`，清掉某 bit，发现 `block_reason` 归零，把线程置 `Ready` 并 `EnqueueReady` + 发 IPI。
2. `Block()` 继续（无锁），把 `state` 改回 `Pended`，并 OR 上新的 `reason`。
3. 结果：线程 `state=Pended`，但**仍挂在就绪队列里**；`WakeThreadOnRecordedCpu` 发出的 IPI 让目标 CPU 以为有活干，`PickNext` 取到的却是一个 `Pended` 线程 → 调度器跳过它或行为未定义。

反向窗口同样致命：`Unblock()` 在 `Block()` 设好 `block_reason` 之前到达 → `Unblock` 看到的 `block_reason` 仍是旧值（不含新 reason）→ 清错 bit → 线程**永久漏唤醒**。

这个窗口在单核下几乎不触发（时序碰巧对齐概率极低），但**4 核下中高频出现**，正好解释了「不使用管道执行普通程序也有小概率卡死」—— 任何 `msg_send` 快路径交付（[message.cpp:163-178](file:///her/mecocoa/mecocoa/message.cpp#L163-L178)）、任何 `msg_recv` 阻塞、任何管道 I/O 阻塞都可能踩中。

`msg_send` 的快路径在 `comm_lock` 下读 `to_th->block_reason` 判定是否直接交付，但 `block_reason` 的写入并不在 `comm_lock` 也不在 `scheduler_lock` 下（见 `Block()`），所以快路径可能读到「正在变成 BR_RecvMsg 但还没写完」的中间态，误判为非阻塞而走 `async_messages.Append` 分支 —— 消息进了异步队列但**没唤醒**接收方，接收方随后才进入 `msg_recv` 并阻塞，于是消息要等到下一次轮询才被取出，若再无新消息则永久挂起。

### 根因 3：`Exet`（execve）不清理 `recv_fo_whom`，且 `Exit` 唤醒父进程依赖快路径

`Taskman::Exet` 在 exec 时清了 `unsolved_msg` 和 `block_reason`，但**没清 `recv_fo_whom`**（见 taskman-new.cpp 中 Exet 片段）。若进程在 exec 之前刚从某次 `sysrecv` 解除阻塞，`recv_fo_whom` 仍指向旧发送方；下一次 `msg_recv` 重设之前，若另一线程按 `recv_fo_whom == fo_th` 匹配，可能把消息误投给已经 exec 过的进程。

对 `wait()` 路径的追踪（结合你给的 dump）：
- shell 调 `wait()` → `sysc_WAIT` → `syssend(Task_TaskMan, WAIT)` + `sysrecv(Task_TaskMan)` → shell 进入 `BR_RecvMsg`，`recv_fo_whom = 线程1`。✓ 与 dump 中 TID9 `RECV=1` 一致。
- `serv_task_loop` 收到 WAIT → `Taskman::Wait` 检查无 zombie 子进程 → 给 shell 加 `BR_Waiting`。
- 子进程退出 → `ExitCurrent` 发 `syssend_async(EXIT)` → `serv_task_loop` 处理 → `Taskman::Exit` 调 `Unblock(BR_Waiting)` + `syssend_async(父pid, ...)`。

问题在于：`Unblock(BR_Waiting)` 只清 `BR_Waiting` bit，shell 仍有 `BR_RecvMsg`，**不会**变 Ready；紧接着的 `syssend_async` 走快路径（`recv_fo_whom==线程1` 且发送方是线程1）清掉 `BR_RecvMsg`，shell 才 Ready。这两步必须**原子里**完成，否则：
- 若 `Exit` 在 `Unblock(BR_Waiting)` 之后、`syssend_async` 之前被抢占/被打断（例如 `serv_task_loop` 在两条语句之间被切走，或 `syssend_async` 因 `LIMIT_THREAD_AMSG=32` 满而返回 3 不交付），shell 的 `BR_Waiting` 清了但 `BR_RecvMsg` 还在 → shell 继续挂死，dump 里 `RECV=1` 永久不消。

这恰好能解释 TID 10、11 已不在 `thchain`（说明 `DestroyThread` 已完成、`Exit` 走完了 `_Exit_Cleanup`）但 shell 仍挂起 —— 唤醒 reply 的最后一步没能把 shell 从 `BR_RecvMsg` 里捞出来。`Exit` 里没有「若 reply 失败则降级为 zombie 等下次 wait」的兜底。

### 修复方向（仅建议，未改代码）

1. **`f_desc_table` 改为用一个独立的全局 `Spinlock` 保护槽位分配**（或改用 per-slot 原子 CAS 占位 `vfile` 字段）。所有 `Open`/`Pipe`/`FileDescriptor_Clone` 在扫描并占用槽位时必须持有该锁；写 `*pfd = *src` 之前先 CAS 标记槽为「占用中」。
2. **`Block()` 全程持 `scheduler_lock`**，或在 `DequeueReady` 之后、设 `state`/`block_reason` 之前不释放锁；`Unblock()` 与 `Block()` 必须以同一把锁互斥。
3. **`Exet` 清理时一并复位 `recv_fo_whom`、`send_to_whom`、`queue_send_*`。**
4. **`Taskman::Exit` 对父进程的唤醒改为「先发 reply 再清 BR_Waiting」或在同一临界区里原子完成**，且 `syssend_async` 失败时应把子进程保留为 zombie 等待下次 `wait()` 重试，而不是直接 `_Exit_Cleanup`。

如需我进一步追踪某条路径的细节（例如 `serv_task_loop` 主循环对 fork/exit 的处理时序，或 `ReadPipe`/`WritePipe` 的唤醒链路），告诉我即可。
