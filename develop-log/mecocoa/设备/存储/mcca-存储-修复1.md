# 20260703


## 发模拟中断信号的问题【未修复】

如果从外部（或 `hd_int_wait` 内部）调 `rupt_proc(Task_Hdd_Serv, ...)` 来伪造信号：

- `hd_int_wait()` 被唤醒、返回 `true`
- 上层 `Harddisk.cpp` 的 `use_loop_fallback = false`，**fallback 不触发**
- 后续 `fn_lup_wait` 检查 DRQ，如果硬件没响应 DRQ 就不会置位，此次 `Read` 会返回 `false` ✅

但是问题来了：**真正的硬件中断可能随后才到来**，这时 `Handint_HDD` 会设 `lock = 1` 并再调一次 `rupt_proc`，往 `Task_Hdd_Serv` 队列里塞一条多余的 INTRUPT 消息。下次 `hd_int_wait()` 一进来就立刻消费掉这条"幽灵消息"，返回 `true`，但实际上那次命令根本还没发出——**造成中断信号错位，一个中断对应着另一个命令**。越来越乱。

---

## 实际应该怎么改

关键在于：`lock` 这个变量已经是正确的状态指示器了：

```
hd_rw_foreback() 把 lock 清 0  → 表示"本次传输开始"
Handint_HDD 把 lock 置 1       → 表示"硬件中断到来"
```

`lock` 的变化和 INTRUPT IPC 消息是**同一个硬件中断的两个副产品**，且 `lock = 1` 发生在 `rupt_proc` 之前。所以可以：

**先轮询 `lock` 等它变 1（有超时），再去收那条 INTRUPT 消息。**

```
hd_int_wait() 改为：
  1. 轮询 lock，等它从 0 变 1（带超时，如 HD_WAITFOR_TIMEOUT 秒）
  2. 超时 lock 还是 0 → return false    ← 触发 fallback 轮询，不留幽灵消息
  3. lock 变 1       → COMM_RECV INTRUPT 消费消息 → return true
```

这样做的好处：

| 情况 | 行为 |
|---|---|
| 中断正常到来 | `lock` 变 1 → 消费 INTRUPT 消息 → 返回 `true` → 正常路径 |
| 中断超时没来 | `lock` 还是 0 → 直接返回 `false` → **INTRUPT 队列里没有多余消息** → `use_loop_fallback` 激活，轮询 DRQ |
| 超时后中断迟到 | `Handint_HDD` 发现 `lock == 1`（已经超时前被别的逻辑置位了？）… |

等等——第三种情况有个微妙之处：超时返回 `false` 时 `lock` 还是 `0`，那后续真中断来了 `Handint_HDD` 还是会执行 `lock = 1` + `rupt_proc`，这条消息依然会进队列。

**这个遗留消息的问题，需要在 `hd_rw_foreback()`（即每次新传输开始时清 `lock` 之前）先把队列里未消费的 INTRUPT 消息丢掉**，或者在 `hd_int_wait` 超时后主动把 `lock` 置 1 以阻止后续的真中断进队列（因为 `Handint_HDD` 看到 `lock != 0` 就直接 EOI 不调 `rupt_proc`）：

```
超时路径：
  lock = 1    ← 主动封住，后续真中断进来会被 Handint_HDD 直接丢弃
  return false
```

这样**彻底没有幽灵消息**，且逻辑自洽：`lock = 1` 的语义就是"本轮传输的中断已处理完"，管它是真中断还是超时放弃，都算"本次结束"。

### 另一个键鼠问题

1. 当您在 GRUB 菜单使用键盘（比如按下回车键选择菜单）时，按键的“断码”（释放按键的信号）或者按键抖动产生的多余数据，会被 PS/2 控制器接收并放入它的输出缓冲区（端口 `0x60`）。
2. 同时，PS/2 控制器会把 IRQ1（键盘中断引脚）**拉高**，请求 CPU 来读取。
3. 但此时 GRUB 已经关闭了中断（`cli`）准备进入您的内核，CPU 就没有去理会这个中断，导致那个按键数据一直死死卡在端口 `0x60` 里，IRQ1 也就一直保持着**高电平**。
4. 当内核启动并配置 APIC/IOAPIC 时，ISA 中断默认是**边沿触发（Edge-Triggered）**的。边沿触发意味着 IOAPIC 只认“从低电平到高电平”的瞬间跳变。
5. 因为 IRQ1 此时已经是高电平了，如果不去把缓冲区里的旧数据读出来，IRQ1 就永远不会回落到低电平，自然也就永远无法产生下一个“上升沿”。所以无论您怎么敲击键盘，IOAPIC 都捕捉不到新的中断信号。另外，由于鼠标和键盘共享同一个 8042 芯片，键盘缓冲区满了也会导致鼠标的数据被堵死。
