/// Hint: Create two threads for each vector.

pub fn parallel_sum(a: Vec<i32>, b: Vec<i32>) -> (i32, i32) {
    let h1 = thread::spawn(move || a.into_iter().sum());
    let h2 = thread::spawn(move || b.into_iter().sum());

    // Join both threads to get results
    (h1.join().unwrap(), h2.join().unwrap())
}

/// Create a named thread that sleeps for the given milliseconds and then returns the input value.
///
/// The thread should be named `"sleeper"`. Use `thread::Builder` to set the name.
/// Inside the thread, call `thread::sleep(Duration::from_millis(ms))` before returning `value`.
///
/// Hint: `thread::sleep` causes the current thread to block; it does not affect other threads.
#[allow(unused_variables)]
pub fn named_sleeper(value: i32, ms: u64) -> i32 {
    // DONE: Create a thread builder with name "sleeper"
    let builder = thread::Builder::new().name("sleeper".into());
    // DONE: Spawn a thread that sleeps for `ms` milliseconds and returns `value`
    let handle = builder.spawn(move || {
        thread::sleep(Duration::from_millis(ms));
        value
    }).unwrap();
    // DONE: Join the thread and return the value
    handle.join().unwrap()
}

### `scoped_slice_sum`

**目标**：不使用 `move` 借用数据。 **核心点**：普通的 `thread::spawn` 要求数据必须是 `'static`（生命周期足够长），因为编译器不知道线程何时结束。`thread::scope` 保证了所有子线程在作用域结束前一定会被 join，因此可以直接借用栈上的数据 `&[i32]`。

```
pub fn scoped_slice_sum(a: &[i32], b: &[i32]) -> (i32, i32) {
    // Use thread::scope to spawn two threads
    // Each thread sums its slice
    // Wait for both threads and return the results
    thread::scope(|s| {
        let h1 = s.spawn(|| a.iter().sum());
        let h2 = s.spawn(|| b.iter().sum());
        (h1.join().unwrap(), h2.join().unwrap())
    })
}
```


### `handle_panic`

**目标**：捕获子线程崩溃。 **核心点**：`join()` 返回的是 `Result<T, Box<dyn Any + Send>>`。如果线程正常结束，返回 `Ok(返回值)`；如果线程 panic 了，返回 `Err`。

```
pub fn handle_panic(value: i32, should_panic: bool) -> Result<i32, ()> {
    // Spawn a thread that either panics or returns value
    let handle = thread::spawn(move || {
        if should_panic {
            panic!("oops");
        }
        value
    });
    // Join and map the result appropriately
    handle.join().map_err(|_| ())//.and_then(|result| result.map_err(|_| ()))
}
```


# Lock: 共享可变状态（Shared Mutable State）

```
//! # Mutex Shared State
//!
//! In this exercise, you will use `Arc<Mutex<T>>` to safely share and modify data between multiple threads.
//!
//! ## Concepts
//! - `Mutex<T>` mutex protects shared data
//! - `Arc<T>` atomic reference counting enables cross-thread sharing
//! - `lock()` acquires the lock and accesses data
```

在 C++ 中，你可能会用 `std::shared_ptr<std::mutex>` 或者全局变量加锁。在 Rust 中，为了保证内存安全，我们通常将 `Arc`（原子引用计数）和 `Mutex`（互斥锁）嵌套使用，俗称 **`Arc<Mutex<T>>` 组合拳**。

作为 C++ 程序员，你可以这样理解这个嵌套结构：

- **`Mutex<T>`**：负责**写权限**。在 Rust 中，`Mutex` 并不只是一个独立的锁对象，它**包裹**着数据。要访问数据，必须先调用 `.lock()`。这保证了同一时间只有一个线程能拿到数据的 `&mut`（可变引用）。
- **`Arc<T>`**：负责**生存期/所有权**。相当于 `std::shared_ptr`。因为 `thread::spawn` 需要 `move` 所有权，如果你直接把一个 `Mutex` 移进第一个线程，第二个线程就没得用了。`Arc` 允许你 `.clone()` 出多份所有权，分发给各个线程。

### `concurrent_counter`：并发计数器

**目标**：多个线程共同累加同一个数字。 **C++ 映射**：多个线程持有一个 `shared_ptr<mutex>` 保护的 `int`。

```
pub fn concurrent_counter(n_threads: usize, count_per_thread: usize) -> usize {
    // 1. 初始化：包裹在 Mutex 里，再套上 Arc 
    let counter = Arc::new(Mutex::new(0));
    let mut handles = vec![];

    for _ in 0..n_threads {
        // 2. 克隆 Arc：增加引用计数，拿到一个新的“智能指针”
        let counter = Arc::clone(&counter);
        
        let handle = thread::spawn(move || {
            for _ in 0..count_per_thread {
                // 3. 加锁：lock() 返回一个 Result，unwrap() 拿到 LockGuard
                // LockGuard 实现了 Deref，所以可以像操作普通变量一样操作它
                let mut num = counter.lock().unwrap();
                *num += 1;
                // 4. 自动解锁：num 离开作用域时，LockGuard 析构，锁自动释放
            }
        });
        handles.push(handle);
    }

    // 等待所有线程结束
    for handle in handles {
        handle.join().unwrap();
    }

    // 5. 最终取值：最后剩下的那个 Arc 依然持有 Mutex
    let final_value = counter.lock().unwrap();
    *final_value
}
```

### `concurrent_collect`：并发收集数据

**目标**：多个线程向同一个 `Vec` 推送数据，最后排序。

```
pub fn concurrent_collect(n_threads: usize) -> Vec<usize> {
    let shared_vec = Arc::new(Mutex::new(Vec::new()));
    let mut handles = vec![];

    for i in 0..n_threads {
        let shared_vec = Arc::clone(&shared_vec);
        let handle = thread::spawn(move || {
            let mut v = shared_vec.lock().unwrap();
            v.push(i);
        });
        handles.push(handle);
    }

    for handle in handles {
        handle.join().unwrap();
    }

    // 取出数据并排序
    // 注意：这里我们使用了 inner.lock().unwrap().clone() 
    // 或者你可以直接用 Arc::try_unwrap(shared_vec).unwrap().into_inner().unwrap() 
    // 来消耗掉 Arc 和 Mutex 拿到里面的 Vec（如果这是最后一份引用的话）
    let mut result = shared_vec.lock().unwrap().clone();
    result.sort();
    result.clone()
}
```

C++ 程序员需要注意的“坑”

 (1) 锁的粒度 (Lock Granularity)

在 `concurrent_counter` 中，我把 `lock()` 放在了 `for` 循环**里面**。

- **后果**：每次加 1 都要竞争锁。这很慢，但能测试并发正确性。
    
- **对比**：如果你把 `let mut num = counter.lock().unwrap();` 放在 `for` 循环**外面**，那么这个线程会一次性加完 100 次才放锁。这实际上变成了**串行执行**。
    

 (2) 死锁 (Poisoning)

Rust 的 `Mutex` 有个很有意思的设计：**毒化 (Poisoning)**。 如果一个线程在持有锁的时候 `panic` 了，这个锁会被标记为“被毒化”。后续线程调用 `lock()` 会返回 `Err`。这就是为什么代码里满是 `lock().unwrap()`——我们的意思是：“如果锁被毒化了，那程序也直接崩溃算了”。
作为一个 C++ 程序员，你可能会觉得奇怪：既然它是阻塞的，那为什么不直接返回 Guard，而是返回一个 Result 呢？
这是 Rust 为了处理 Panic 安全（Panic Safety） 设计的：
如果线程 A 拿到了锁，但在释放锁之前 panic 了，这个数据可能正处于某种“非法”的中间状态（即数据被破坏了）。此时锁会被标记为 Poisoned（中毒）。
当线程 B 尝试 lock() 时，虽然它能成功阻塞并等到锁释放，但 lock() 会返回一个 Err，告诉你：“锁我给你拿到了，但里面的数据可能坏了，你自己看着办。”
这就是为什么你总是看到 lock().unwrap()。unwrap() 的意思是：“如果数据坏了，我也跟着 panic 掉，保证错误不蔓延”。

 (3) RAII 释放锁

在 C++ 中，你可能用 `std::lock_guard<std::mutex> lock(m);`。 在 Rust 中，`let guard = mutex.lock().unwrap();` 就是 RAII。锁会在 `guard` 离开作用域时自动释放。如果你想提前释放，可以手动调用 `drop(guard);`。

在 Rust 的标准库中，`std::sync::Mutex::lock()` 的行为是 **阻塞（Blocking）**，而不是忙等（Busy-waiting/Spinning），也不是直接返回失败。

为了让你更透彻地理解，我们分三个维度来看：

1.它的行为：阻塞（Blocking）

当线程执行到 `lock()` 但发现锁已被占用时：
- **不消耗 CPU**：该线程会被操作系统挂起（Park）。它会从 CPU 的运行队列中移除，进入等待队列。
- **由内核唤醒**：当持有锁的线程释放锁（`MutexGuard` 析构）时，操作系统会挑选一个等待中的线程并将其唤醒，使其重新获得执行机会。
- **对比 C++**：这完全等同于 C++ 中的 `std::mutex::lock()`。

2.如果你想“返回失败”：`try_lock()`

如果你不希望线程停下来死等，而是想“如果有锁我就干活，没锁我就先去干别的”，你应该使用 `try_lock()`。

- **行为**：立即返回。
- **返回值**：
    - `Ok(Guard)`：成功拿到锁。
    - `Err(TryLockError::WouldBlock)`：锁正被别人占着，拿不到。
    - `Err(TryLockError::Poisoned)`：锁被毒化了（之前的线程带着锁 panic 了）。

3.如果你想“忙等”：Spinlock

忙等（Spinning）通常是指在一个 `while` 循环里不断检查锁的状态，直到拿到锁为止。
- **标准库不提供**：Rust 标准库的 `Mutex` 是跨平台的重型锁，基于操作系统的原语（如 Linux 的 `futex` 或 Windows 的 `SRWLock`）。
- **第三方库**：如果你在做高性能开发（比如延迟极低、锁持有时间极短的场景），可以使用类似 `spin` 这样的 crate 提供的 `Spinlock`。


# channel

Go 语言有一句名言：“**不要通过共享内存来通信，而要通过通信来共享内存。**” Rust 的 `mpsc` 频道就是这一哲学的体现。

`mpsc` 代表 **Multi-Producer, Single-Consumer**（多生产者，单消费者）。

- **Sender (tx)**：像个“传声筒”。你可以克隆（`clone`）很多个传声筒分发给不同线程。
- **Receiver (rx)**：像个“听筒”。只能有一个，留在处理数据的线程里。
- **所有权转移**：这是 Rust Channel 最强大的地方。当你 `send` 一个 `String` 时，**所有权**真的通过管道传过去了。发送方之后再也无法使用这个字符串，彻底消除了数据竞争。

`simple_send_recv`：基础发送与接收

**目标**：在一个线程发，一个线程收。

```
pub fn simple_send_recv(items: Vec<String>) -> Vec<String> {
    // 1. 创建频道，返回 (发送者, 接收者)
    let (tx, rx) = mpsc::channel();

    // 2. 创建生产者线程
    thread::spawn(move || {
        for item in items {
            // send 会把 item 的所有权移入频道
            tx.send(item).unwrap();
        }
        // 线程结束，tx 离开作用域被自动 drop
    });

    // 3. 在主线程接收
    // 技巧：rx 本身可以作为一个迭代器使用！
    // 当所有的 tx 都被销毁时，迭代器会自动结束循环。
    rx.into_iter().collect()
}
```



`multi_producer`：多生产者模式

**目标**：克隆多个发送者，并处理“关闭频道”的陷阱。

**C++ 映射**：想象你在写一个日志系统，所有工作线程（Producers）都往同一个 IO 线程（Consumer）发消息。

```
pub fn multi_producer(n_producers: usize) -> Vec<String> {
    let (tx, rx) = mpsc::channel();

    for id in 0..n_producers {
        // 每个线程都需要自己的发送者副本
        let tx_clone = tx.clone();
        
        thread::spawn(move || {
            let msg = format!("msg from {}", id);
            tx_clone.send(msg).unwrap();
        });
    }

    // --- 关键陷阱 ---
    // 此时主线程里还持有一个最初的 `tx`。
    // 如果不手动 drop 它，rx 永远不会知道“所有生产者都干完活了”，
    // 导致 rx.iter() 永远阻塞，程序无法结束。
    drop(tx); 

    let mut result: Vec<String> = rx.into_iter().collect();
    result.sort(); // 题目要求排序
    result
}
```

---

 (1) 为什么 `rx` 会结束？

在 C++ 中，如果你用 `std::condition_variable` 配合 `std::deque` 做队列，你通常得手动发一个“结束标志”（哨兵值，如 `nullptr`）告知消费者停止。

在 Rust 中，频道关闭是**基于引用计数**的：
- 当所有的 `Sender` (tx) 都被析构（drop）时，管道关闭。
- `Receiver::recv` 会返回 `Err`。
- `rx.into_iter()` 循环会自然结束。
- **这就是为什么 `multi_producer` 里一定要 `drop(tx)`** —— 因为主线程里的那个 `tx` 如果不丢弃，引用计数就永远不会降到 0。
 (2) 阻塞行为
- **`rx.recv()`**：阻塞式。如果没消息，线程就睡觉（类似 `std::condition_variable::wait`）。
- **`tx.send()`**：对于 `mpsc::channel`（异步频道），它是**非阻塞**的，缓冲区理论上是无限的（可能会耗尽内存）。
- **`mpsc::sync_channel`**：Rust 也提供同步频道（有界缓冲区）。如果缓冲区满了，`send` 会阻塞。这在 C++ 中对应固定大小的环形队列。
 (3) 性能
Rust 的 `mpsc` 是高度优化的无锁（lock-free）或轻量级锁实现的。相比于你自己用 `std::mutex<std::vector>` 封装，它的吞吐量通常更高，且逻辑更清晰。

运行程序并一次性拿回所有输出。

```
pub fn run_command(program: &str, args: &[&str]) -> String {
    let output = Command::new(program)
        .args(args)
        .stdout(Stdio::piped()) // 显式重定向 stdout 到管道
        .output()               // 阻塞直到进程结束
        .expect("Failed to execute command");

    // output.stdout 是 Vec<u8>，需要转成 String
    String::from_utf8_lossy(&output.stdout).to_string()
}

`pipe_through_cat`：双向管道通信（重点）

**关键点**：为什么必须 `drop(stdin)`？ 在 C++ 中，如果你打开了一个管道写端而不关闭，读端的 `cat` 会一直阻塞等待输入。Rust 利用**所有权**解决了这个问题：当你 `drop` 掉 `stdin` 对象，底层文件描述符自动关闭。

> expect 是带参数的 unwrap

```
pub fn pipe_through_cat(input: &str) -> String {
    let mut child = Command::new("cat")
        .stdin(Stdio::piped())
        .stdout(Stdio::piped())
        .spawn() // 使用 spawn，因为我们需要在子进程运行时与其交互
        .expect("Failed to spawn cat");

    // 1. 获取 stdin 的所有权并写入数据
    // 使用 take() 是因为 Child 结构体拥有 stdin 的 Option，拿出来后 Child 就不再拥有它
    let mut stdin = child.stdin.take().expect("Failed to open stdin");
    stdin.write_all(input.as_bytes()).expect("Failed to write to stdin");
    
    // 2. 显式关闭 stdin！
    // 只有关闭了写端，cat 才知道输入结束了，才会处理并退出。
    drop(stdin); // Close the write end to signal EOF

    // 3. 读取 stdout
    let mut output = String::new();
    child.stdout.take().expect("Failed to open stdout")
        .read_to_string(&mut output).expect("Failed to read stdout");

    // 4. 等待进程彻底结束（回收僵尸进程）
    child.wait().expect("Wait failed");
    
    output
}
```

### `get_exit_code`：获取退出状态

**目标**：类似于 C++ 中检查 `WEXITSTATUS(status)`。

```
pub fn get_exit_code(command: &str) -> i32 {
    let status = Command::new("sh")
        .args(["-c", command])
        .status() // 只关心退出状态，不关心输出内容
        .expect("Failed to execute shell");

}
```

在 `run_command_with_result` 中，你会接触到如何把系统级错误（如：找不到命令 `ENOENT`）传给上层。

### `pipe_through_grep`：复杂过滤

这个逻辑与 `cat` 类似，但展示了如何处理命令行参数。

```
pub fn pipe_through_grep(pattern: &str, input: &str) -> String {
    let mut child = Command::new("grep")
        .arg(pattern)
        .stdin(Stdio::piped())
        .stdout(Stdio::piped())
        .spawn()
        .expect("Failed to spawn grep");

    // 写入数据
    let mut stdin = child.stdin.take().unwrap();
    stdin.write_all(input.as_bytes()).unwrap();
    drop(stdin); // 发送 EOF

    // 读取结果
    let mut output = String::new();
    child.stdout.take().unwrap().read_to_string(&mut output).unwrap();
    
    child.wait().unwrap();
    output
}
```


### (1) `take().unwrap()` 模式

在 Rust 的 `Child` 结构体中，`stdin`、`stdout` 和 `stderr` 的类型是 `Option<ChildStdin>` 等。

- **为什么是 Option？** 因为你可能在启动时选择了 `Stdio::inherit()`（继承父进程），这时它们就是 `None`。
- **为什么要 `take()`？** 就像 C++ 的 `std::move`。你需要把这个 IO 句柄从进程句柄中“抽离”出来单独操作。一旦 `take` 出来，该句柄离开作用域时就会关闭管道。
    

### (2) 僵尸进程与 `wait`

和 C++ 一样，子进程结束后如果不调用 `wait()`（或者在 Rust 中调用 `output()`/`status()`，它们内部调了 wait），子进程会变成**僵尸进程**。

- Rust 的 `Child` 对象在被 `drop` 时**不会**自动 `wait`（这与一些人的直觉相反）。如果你 `spawn` 了一个进程却不管它，它可能会变成孤儿进程或僵尸进程。

### 总结

- 如果你只需要结果：用 `.output()`。
- 如果你需要持续交互：用 `.spawn()` + `take()` 句柄 + `drop(stdin)`。
- 记得处理编码：系统命令返回的是字节流（`Vec<u8>`），需要转为 `String`。

# 原子操作（Atomic Operations）

在 C++ 中， `std::atomic<uint64_t>`。Rust 的原子类型（如 `AtomicU64`）在 API 设计和内存模型（Memory Ordering）上几乎与 C++11 标准完全对齐。它们允许你在不使用 `Mutex`（互斥锁）的情况下，实现高性能的线程安全操作。

```
impl AtomicCounter {
    pub fn increment(&self) -> u64 {
        // fetch_add 返回增加前的值
        self.value.fetch_add(1, Ordering::Relaxed)
    }

    pub fn decrement(&self) -> u64 {
        self.value.fetch_sub(1, Ordering::Relaxed)
    }

    pub fn get(&self) -> u64 {
        self.value.load(Ordering::Relaxed)
    }

    pub fn compare_and_swap(&self, expected: u64, new_val: u64) -> Result<u64, u64> {
        // compare_exchange 返回 Result<T, T>
        // Ok 表示成功，Err 表示当前值不匹配
        self.value.compare_exchange(
            expected, 
            new_val, 
            Ordering::AcqRel, // 成功时的排序
            Ordering::Acquire  // 失败时的排序
        )
    }

    pub fn fetch_multiply(&self, multiplier: u64) -> u64 {
        let mut current = self.get();
        loop {
            let new = current * multiplier;
            // CAS 循环：尝试更新，如果期间值变了，compare_exchange 会返回最新的值
            match self.compare_and_swap(current, new) {
                Ok(old) => return old,
                Err(actual) => current = actual, // 更新 current 并重试
            }
        }
    }
}

# 内存屏障（Memory Barriers）与重排（Reordering）

CPU 和编译器为了优化性能，会乱序执行指令。如果两个线程在没有同步的情况下通信，可能会出现“旗标已设为 true，但数据还没写入内存”的诡异现象。

这是理解现代多核同步的关键（对应 C++11 的 `std::memory_order_release` 和 `acquire`）：

- **`Release` (发布)**：像是一道“防火墙”，确保所有在它**之前**的写操作，都不会被重排到它**之后**。
- **`Acquire` (获取)**：确保所有在它**之后**的读操作，都不会被重排到它**之前**。
- **同步点**：当线程 A 用 `Release` 写入变量 $V$，且线程 B 用 `Acquire` 读取变量 $V$ 并读到了 A 写入的值时，线程 A 在 `Release` 之前的所有写入操作，对线程 B 来说都是可见的。

FlagChannel：经典的发布-获取同步
目标：线程 A 传一个 u32 给线程 B，不能用锁。

```
impl FlagChannel {
    pub fn produce(&self, value: u32) {
        // 1. 先写数据。这里的排序可以是 Relaxed，
        // 因为我们靠后面的 ready 操作来划定边界。
        self.data.store(value, Ordering::Relaxed);

        // 2. 设置旗标。必须使用 Release！
        // 告诉 CPU：上面的 data store 必须在 ready 变为 true 之前完成。
        self.ready.store(true, Ordering::Release);
    }

    pub fn consume(&self) -> u32 {
        // 1. 忙等旗标。必须使用 Acquire！
        // 只有读到 true 且使用 Acquire，才能建立同步关系。
        while !self.ready.load(Ordering::Acquire) {
            // 在忙等时可以加上 hint 来节省能耗（类似 C++ 的 _mm_pause()）
            std::hint::spin_loop(); 
        }

        // 2. 读数据。既然建立了 Acquire 关系，这里的读操作一定能看到 produce 写入的最新值。
        self.data.load(Ordering::Relaxed)
    }
}
```

OnceCell：一次性初始化
目标：模拟 std::sync::Once，确保只有一个线程成功初始化。

```
impl OnceCell {
    pub fn init(&self, val: u32) -> bool {
        // 使用 compare_exchange 实现 CAS。
        // 成功时使用 SeqCst（最强顺序），失败时使用 Acquire（确保能看到赢家写的 value）。
        match self.initialized.compare_exchange(
            false, 
            true, 
            Ordering::SeqCst, 
            Ordering::Acquire
        ) {
            Ok(_) => {
                // 只有赢家进入这里
                self.value.store(val, Ordering::SeqCst);
                true
            }
            Err(_) => false, // 输家直接返回
        }
    }

    pub fn get(&self) -> Option<u32> {
        // 使用 Acquire 读，确保能看到 init 线程写入的 value
        if self.initialized.load(Ordering::Acquire) {
            Some(self.value.load(Ordering::Relaxed))
        } else {
            None
        }
    }
}
```


(1) `SeqCst`：最强的核武器

`Ordering::SeqCst` 对应 `std::memory_order_seq_cst`。
- 它是 Rust 原子操作的**默认排序**（如果你直接调用 `compare_and_swap` 这种老 API）。
- 它保证了**全局一致的执行顺序**。但在 x86_64 以外的架构（如 ARM）上，它会插入非常昂贵的内存屏障指令，显著降低性能。
- **建议**：除非你正在实现非常复杂的锁算法，否则优先考虑 `Release/Acquire`。
    

 (2) 为什么 `data` 可以用 `Relaxed`？

在 `FlagChannel` 中，`data` 本身并不负责同步逻辑。同步的“重量级任务”交给了 `ready`。 只要 `ready` 确立了 `Release-Acquire` 对，它就会形成一个 **happens-before** 关系。你可以想象 `ready` 的 `Release` 是一把推力，把 `data` 的写入强行推过了线程边界。

 (3) `std::hint::spin_loop()`

在 C++ 中，你会用 `__builtin_ia32_pause()`。在 Rust 中，这有助于告诉 CPU 这个线程正在自旋，CPU 可以暂时降低功耗或让出超线程资源给同核的另一个线程。

**如何选择 Ordering**

|**场景**|**推荐排序**|**理由**|
|---|---|---|
|**纯计数器**|`Relaxed`|只要操作是原子的，不关心指令重排。|
|**标志位/信号**|`Release` (写), `Acquire` (读)|需要确保“数据准备好了”这种先后顺序。|
|**互斥锁实现**|`AcqRel`|锁的释放和获取需要双向保护。|
|**完全蒙圈时**|`SeqCst`|虽然慢，但最安全，符合人类逻辑。|

# 自旋锁 (Spin Lock)

当拿不到锁时，线程不会睡眠（不让出 CPU），而是原地打转（自旋），直到拿到锁为止。

### `UnsafeCell<T>`

这是 C++ 程序员理解 Rust 内部可变性的关键。

- **痛点**：Rust 的 `lock(&self)` 接收的是**不可变引用**，但它必须返回一个**可变引用** `&mut T`。这在常规 Rust 语法下是不可能的。
- **解药**：`UnsafeCell<T>` 是 Rust 中唯一可以合法绕过借用检查器（Borrow Checker）的手段。
- **C++ 类比**：它类似于 C++ 中的 `mutable` 关键字，但更强大。它告诉编译器：“这个字段的内存可能在任何时候被改变，不要对它做过于激进的别名优化（Alias Optimization）。”
- **用法**：通过 `self.data.get()` 获得一个原始指针 `*mut T`，然后将其转回引用。

```
pub fn lock(&self) -> &mut T {
    // 1. 进入自旋循环
    while self.locked.compare_exchange(
        false,            // 期望值：锁是开着的
        true,             // 目标值：把它锁上
        Ordering::Acquire, // 成功时：获取语义（确保看到之前解锁线程的修改）
        Ordering::Relaxed  // 失败时：没拿到锁，不需要任何顺序保证
    ).is_err() {
        // 2. 没拿到锁，告诉 CPU 我在自旋，节省点电
        core::hint::spin_loop();
    }

    // 3. 成功拿到锁，把 UnsafeCell 里的原始指针转为 &mut T
    // 安全性：因为我们刚刚成功设置了 locked 为 true，所以目前只有我们持有锁
    unsafe { &mut *self.data.get() }
}

pub fn unlock(&self) {
    // 使用 Release 语义。
    // 这保证了在设置 locked = false 之前，所有对数据的修改都已写入内存，
    // 并且对下一个 Acquire 锁的线程可见。
    self.locked.store(false, Ordering::Release);
}

pub fn try_lock(&self) -> Option<&mut T> {
    // 只尝试一次，不写循环
    if self.locked.compare_exchange(
        false, 
        true, 
        Ordering::Acquire, 
        Ordering::Relaxed
    ).is_ok() {
        unsafe { Some(&mut *self.data.get()) }
    } else {
        None
    }
}
```

 (1) `unsafe impl Sync for SpinLock<T>`

由于我们手动管理了并发访问（通过 `AtomicBool`），我们需要告诉 Rust 编译器：**“相信我，这个结构体在多线程之间共享是安全的。”**

- `Sync`：允许多个线程同时持有 `&SpinLock`。
- 条件是 `T: Send`：如果数据本身不能发给另一个线程，那锁着它也没意义。
    

 (2) 为什么返回 `&mut T` 是危险的？

这个练习里的 `lock` 返回的是一个**裸引用**。这在实际生产代码中是**非常不推荐**的，因为：
- 用户可能会忘记调用 `unlock()`（导致死锁）。
- 用户可能在调用了 `unlock()` 之后，依然持有并使用之前拿到的 `&mut T`（导致 Data Race）。

**正宗的 Rust 写法**：应该返回一个包装了引用的 **`SpinLockGuard`**，并为其实现 `Drop` trait。这样当 Guard 离开作用域时，会自动调用 `unlock()`。

(3) 与 `std::mutex` 的区别

- `SpinLock`：在多核环境下非常快，因为没有上下文切换。但如果锁被占用时间长，会白白浪费 CPU。
- `std::mutex`：在拿不到锁时会通知内核挂起线程。适合锁持有时间长、或者单核 CPU 的情况。

设计一个安全的库

在 C++ 中，我们习惯用 `std::lock_guard` 来防止忘记 `unlock`。Rust 的 **RAII (Resource Acquisition Is Initialization)** 更加强大，因为它利用所有权系统确保：**只要你持有 Guard，数据就是安全的；一旦 Guard 消失，锁就一定会被释放。**

```
pub fn lock(&self) -> SpinGuard<'_, T> {
	// 自旋直到拿到锁
	while self.locked.compare_exchange(
		false, 
		true, 
		Ordering::Acquire, 
		Ordering::Relaxed
	).is_err() {
		std::hint::spin_loop();
	}
	// 将 self 的引用包装进 Guard
	SpinGuard { lock: self }
}

impl<T> Drop for SpinGuard<'_, T> {
    fn drop(&mut self) {
        // 释放锁。使用 Release 确保之前的修改对其他线程可见。
        self.lock.locked.store(false, Ordering::Release);
    }
}
```

`Deref` & `DerefMut`：让 Guard 表现得像数据本身

这两个 Trait 实现了“透明访问”。你在代码里写 `*guard = 42` 时，编译器会自动调用这些方法。

```
impl<T> Deref for SpinGuard<'_, T> {
    type Target = T;

    fn deref(&self) -> &T {
        // 安全性：拿到 Guard 意味着已经通过了 lock() 的 CAS 校验
        unsafe { &*self.lock.data.get() }
    }
}

impl<T> DerefMut for SpinGuard<'_, T> {
    fn deref_mut(&mut self) -> &mut T {
        unsafe { &mut *self.lock.data.get() }
    }
}
```

(1) `SpinGuard<'a, T>` 中的 `'a` 是什么？
这是 **生命周期标注 (Lifetime)**。
- **含义**：它告诉编译器：“`SpinGuard` 存活的时间**不能超过**它引用的那个 `SpinLock`。”
- **C++ 对应**：在 C++ 中，如果你把一个 `lock_guard` 传给另一个线程，而原本的 `mutex` 被销毁了，程序会发生 UB（未定义行为）。Rust 在编译期就掐死了这种可能。

(2) 为什么 Rust 的锁“包裹”着数据？
这是 Rust 区别于 C++/C 最精妙的设计：
- **C++ 做法**：`std::mutex m; int data;`。锁和数据是分离的，程序员必须**自觉**记得在访问 `data` 前给 `m` 加锁。
- **Rust 做法**：`SpinLock<T>` 把数据塞进锁里。如果不调用 `.lock()` 拿到 `Guard`，你**物理上无法**访问到内部的 `T`。
- **结论**：Rust 把“程序员的自觉”变成了“编译器的强制”。

(3) Panic 安全性 (Panic Safety)
如果你的线程在持有锁时发生了 `panic!`：
- **C 语言**：如果你手动调用的 `unlock` 在 `panic` 之后，锁就永远死锁了。
- **Rust/C++ (RAII)**：当线程栈展开（Unwind）时，局部变量 `guard` 会被销毁，自动触发 `drop`。这意味着锁会被释放，其他线程可以继续运行。这就是测试用例 `test_panic_safety` 验证的内容。
    
语法进阶：`&*` 和 `&mut *`
你可能觉得 `unsafe { &mut *self.lock.data.get() }` 很绕。

- `self.lock.data.get()` -> 返回 `*mut T` (裸指针)。
- `*` -> 解引用，拿到内容。
- `&mut` -> 重新借用，变成 Rust 的安全引用。

**这个过程本质上是：将一个“没有任何规则约束的 C 指针”重新绑定到“受 Rust 生命周期管理的引用”上。**

# 读写锁（Read-Write Lock）

我们只用一个 `AtomicU32` 就管理了三种状态。这种把一个整数拆成几块用的技巧，在 Linux 内核源码（如 `rwsem`）中随处可见。

|**位 (Bits)**|**含义**|**作用**|
|---|---|---|
|**0 - 29**|**Reader Count**|记录当前有多少个读者。|
|**30**|**WRITER_HOLDING**|1 表示当前有写者正在修改数据。|
|**31**|**WRITER_WAITING**|1 表示有写者在排队。**写者优先**的关键。|

`read`：读者进入

**写者优先原则**：只要有写者在等（`WRITER_WAITING`），即便现在锁是空闲的，新来的读者也必须排队，防止写者被“饿死”。

```
pub fn read(&self) -> RwLockReadGuard<'_, T> {
    loop {
        let s = self.state.load(Ordering::Acquire);
        // 如果有写者拿着锁，或者有写者在排队，读者就自旋
        if (s & (WRITER_HOLDING | WRITER_WAITING)) != 0 {
            std::hint::spin_loop();
            continue;
        }
        // 尝试读者计数 +1
        if self.state.compare_exchange_weak(
            s, s + 1, Ordering::AcqRel, Ordering::Acquire
        ).is_ok() {
            return RwLockReadGuard { lock: self };
        }
    }
}
```

`write`：写者抢占

写者的逻辑分为两步：先“插队”，再“清场”。

```
pub fn write(&self) -> RwLockWriteGuard<'_, T> {
    // 1. 宣告：我要写了！(设置 WRITER_WAITING)
    // 这一步之后，新来的读者都会被堵在 read() 的入口
    self.state.fetch_or(WRITER_WAITING, Ordering::Release);

    loop {
        let s = self.state.load(Ordering::Acquire);
        // 2. 等待清场：必须没有读者且没有其他写者拿着锁
        if (s & READER_MASK) == 0 && (s & WRITER_HOLDING) == 0 {
            // 3. 尝试正式拿锁：把 WAITING 标志转为 HOLDING 标志
            let next = (s & !WRITER_WAITING) | WRITER_HOLDING;
            if self.state.compare_exchange_weak(
                s, next, Ordering::AcqRel, Ordering::Acquire
            ).is_ok() {
                return RwLockWriteGuard { lock: self };
            }
        }
        std::hint::spin_loop();
    }
}

// : Implement Deref for RwLockReadGuard
// Return shared reference to data: unsafe { &*self.lock.data.get() }
impl<T> Deref for RwLockReadGuard<'_, T> {
    type Target = T;

    fn deref(&self) -> &T {
        unsafe { &*self.lock.data.get() }
    }
}
// : Implement Drop for RwLockReadGuard
// Decrement reader count: self.lock.state.fetch_sub(1, Ordering::Release)
impl<T> Drop for RwLockReadGuard<'_, T> {
    fn drop(&mut self) {
        self.lock.state.fetch_sub(1, Ordering::Release);
    }
}
```


RAII Guards 实现

这里的 Guard 逻辑和 SpinLock 类似，但 Drop 的操作完全不同。

RwLockReadGuard 的释放：只需将读者计数减 1。
```
impl<T> Drop for RwLockReadGuard<'_, T> {
    fn drop(&mut self) {
        self.lock.state.fetch_sub(1, Ordering::Release);
    }
}
```

RwLockWriteGuard 的释放：必须同时清除 HOLDING 和 WAITING 位。

```
impl<T> Drop for RwLockWriteGuard<'_, T> {
    fn drop(&mut self) {
        self.lock.state.fetch_and(!(WRITER_HOLDING | WRITER_WAITING), Ordering::Release);
    }
}
```


# 异步编程 future

作为 C++ 程序员，你可以将 Rust 的 `Future` 理解为一种**显式的、高度优化的状态机**。它非常类似于 C++20 的 `std::coroutine`，但设计上更强调“无堆分配”（Zero-cost abstraction）。

在 Rust 中，异步不是由后台线程自动完成的，而是一场“拉锯战”：

- **`Future`**：是一个状态机，它只在被 **`poll`**（轮询）时才会执行一段逻辑。
- **`Poll::Pending`**：告诉运行时（Executor）：“我现在还没好，等会再来。”
- **`Poll::Ready(T)`**：告诉运行时：“我好了，这是你要的结果。”
- **`Waker`**：这是关键！如果 Future 返回了 `Pending`，它必须负责在将来某个时刻调用 `waker.wake()`。这就像是给运行时发个短信：“嘿，我现在有进展了，快来再 `poll` 我一次！”

倒计时状态机 这个 Future 模拟了一个需要多次轮询才能完成的任务。
```
impl Future for CountDown {
    type Output = &'static str;

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.count == 0 {
            // 状态 1：完成
            Poll::Ready("liftoff!")
        } else {
            // 状态 2：未完成
            self.count -= 1;
            
            // 重要：必须通知运行时“我还没完，请继续轮询我”
            // 在真实场景中，这通常由硬件中断或 IO 事件触发
            cx.waker().wake_by_ref(); 
            
            Poll::Pending
        }
    }
}
```

只礼让一次 这是理解异步控制流的经典例子。第一次调用返回 `Pending`，迫使执行器暂时挂起它。

```
impl Future for YieldOnce {
    type Output = ();

    fn poll(mut self: Pin<&mut Self>, cx: &mut Context<'_>) -> Poll<Self::Output> {
        if self.yielded {
            // 第二次被 poll：已经礼让过了，现在可以结束了
            Poll::Ready(())
        } else {
            // 第一次被 poll：标记为已礼让
            self.yielded = true;
            
            // 同样要唤醒 waker，否则执行器可能永远不会再次 poll 它
            cx.waker().wake_by_ref();
            
            Poll::Pending
        }
    }
}
```

 (1) `Pin<&mut Self>` 是什么？
这是 Rust 异步中最让初学者头疼的概念。
- **C++ 背景**：C++ 协程会将状态保存在堆上（Coroutine Frame）。
- **Rust 做法**：Rust 倾向于将 Future 存在栈上。但如果 Future 内部有指向自己成员的引用（自引用结构），一旦在内存中移动位置，指针就失效了。
- **`Pin` 的作用**：它是一个标记，保证对象在内存中的地址**不再改变**。只有被 `Pin` 住的对象，才能安全地执行 `poll`。对于不包含自引用的简单结构（如本题），可以用 `self.get_mut()` 轻松拿到可变引用。
(2) 为什么要在返回 `Pending` 之前 `wake()`？
在测试用例中，如果你不调用 `wake()`，`tokio::test` 会直接挂起并报错“检测到死锁”
- 因为 Rust 的运行时是非常“懒”的：如果没有人明确告诉它某个 Future 准备好了，它为了省电和性能，永远不会主动去猜。
 (3) 性能优越性
你会发现，手动实现的 `Future` 没有任何隐藏的内存分配。这在嵌入式或高并发系统级编程中具有巨大的性能优势，完全对标 C++ 的“零开销原则”。

# Tokio —— Rust 最流行的异步运行时

这一章我们将从手动编写 `Future` 状态机的“苦差事”中解脱出来，进入 **Tokio** —— Rust 最流行的异步运行时。

如果你有 C++ 背景，可以把 **Tokio Task** 类比为极其轻量级的线程（类似 Go 的 Goroutine），而 `tokio::spawn` 则类似于 `std::async(std::launch::async, ...)`，但它是由 Tokio 的调度器（通常是多线程工作窃取调度器）来管理的。

并发地计算 $0..n$ 每个数字的平方并保持顺序。
```
pub async fn concurrent_squares(n: usize) -> Vec<usize> {
    let mut handles = Vec::new();

    for i in 0..n {
        // tokio::spawn 会将任务提交给调度器立即开始执行
        // 它返回一个 JoinHandle，这本身就是一个 Future
        let handle: JoinHandle<usize> = tokio::spawn(async move {
            i * i
        });
        handles.push(handle);
    }

    let mut results = Vec::new();
    for handle in handles {
        // 等待任务完成。注意：JoinHandle 的 await 返回的是 Result<T, JoinError>
        // 如果任务内部 panic 了，这里会返回 Err
        match handle.await {
            Ok(res) => results.push(res),
            Err(e) => panic!("Task panicked: {:?}", e),
        }
    }
    results
}
```

证明任务是**并发**执行的，总耗时应该接近单次 `sleep` 的时间。
```
pub async fn parallel_sleep_tasks(n: usize, duration_ms: u64) -> Vec<usize> {
    let mut handles = Vec::new();

    for i in 0..n {
        let handle = tokio::spawn(async move {
            sleep(Duration::from_millis(duration_ms)).await;
            i
        });
        handles.push(handle);//  wait
    }

    let mut results = Vec::new();
    for handle in handles {
        results.push(handle.await.unwrap());
    }

    // 题目要求排序返回
    results.sort();
    results
}
```

 (1) `tokio::spawn` vs `std::thread::spawn`

- **资源占用**：`std::thread` 申请的是 OS 线程，通常占用 1MB+ 栈空间；`tokio::spawn` 申请的是一个 **Task**，初始内存占用仅约几百字节。
- **调度**：`thread` 由操作系统内核调度；`task` 由 Tokio 在用户态调度。这就像我们在上一章实现的绿线程，只不过 Tokio 的性能要强悍得多。
    

 (2) 为什么需要 `async move`？

在 C++ Lambda 中，你可能写 `[=]`。在 Rust 的 `tokio::spawn` 中，闭包必须是 `move` 的。
- **原因**：因为 Tokio Task 的生命周期必须是 `'static`。调度器可能会在任何线程上、任何时间运行这个任务，它必须拥有其内部数据的所有权，不能包含对当前函数栈帧的引用。

 (3) `await` 会阻塞吗？

**绝对不会。** 当你在执行 `handle.await` 时：
1. 如果任务没完，当前线程会**挂起当前任务**，去运行执行器队列里的其他任务。
2. 这对应于你在 C++ 中使用协同程序（Coroutines）时的 `co_await`，而不是 `future.get()`。`future.get()` 会卡死整个物理线程，而 `await` 只会礼让。

# 在 Tokio 中使用 MPSC 异步频道

作为 C++ 程序员，你可以把这看作是一个**内置了协程挂起机制的 `std::deque` + `std::condition_variable`**。

在两个异步任务之间传递字符串。
```
pub async fn producer_consumer(items: Vec<String>) -> Vec<String> {
    // 1. 创建频道。Tokio 的 mpsc 是有界的（bounded），必须指定容量。
    let (tx, mut rx) = mpsc::channel(items.len().max(1));

    // 2. 产生者任务
    tokio::spawn(async move {
        for item in items {
            // send 是异步的，如果频道满了会 await
            if let Err(_) = tx.send(item).await {
                break; // 接收端关了
            }
        }
    });

    // 3. 消费者逻辑（直接在当前函数作为消费者）
    let mut results = Vec::new();
    // recv() 返回 Option<T>，None 表示所有 Sender 都已丢弃且频道已空
    while let Some(item) = rx.recv().await {
        results.push(item);
    }

    results
}
```

多个生产者向同一个接收者发送消息。这是异步编程中最常见的模式（例如：多个网络连接将数据汇聚到日志处理器）。
```
pub async fn fan_in(n_producers: usize) -> Vec<String> {
    let (tx, mut rx) = mpsc::channel(n_producers);

    for id in 0..n_producers {
        let tx_clone = tx.clone();
        tokio::spawn(async move {
            let msg = format!("producer {}: message", id);
            let _ = tx_clone.send(msg).await;
        });
    }

    // --- 关键点 ---
    // 必须丢弃当前函数持有的原始 tx。
    // 频道关闭的条件是：引用计数归零。如果不丢弃这个，rx.recv() 永远不会返回 None。
    drop(tx);

    let mut results = Vec::new();
    while let Some(msg) = rx.recv().await {
        results.push(msg);
    }

    results.sort();
    results
}
```

 (1) 背压 (Backpressure)

在 C++ 中实现生产消费者时，如果生产者太快，内存会爆炸。 Tokio 的 `mpsc::channel(capacity)` 强制要求容量。如果达到上限，`tx.send(...).await` 会暂停执行，直到消费者取走数据。这种内置的**背压机制**是构建稳定分布式系统的基石。

 (2) 为什么 `rx` 要用 `mut`？

在 Rust 中，`rx.recv()` 会修改 `Receiver` 内部的状态（更新读取位置等），所以需要 `mut`。而 `tx.send()` 只需要 `&self`（虽然它内部会通过原子操作修改状态），这允许我们在不使用 `Mutex` 的情况下直接克隆 `tx`。

 (3) 自动取消 (Cancellation)

如果 `Receiver` 被丢弃了，所有的 `Sender.send().await` 都会立即返回错误。

- **对应 C++**：你需要手动关闭 `condition_variable` 并通知所有等待者。
- **Rust 做法**：利用 **RAII** 自动完成。如果消费者任务因为报错退出了，生产者任务也会因为 `send` 失败而自然结束。

- **有界频道**：永远使用 `mpsc::channel(n)` 而不是无界频道，除非你确定内存不是问题。
- **关闭通知**：通过 `drop(tx)` 来优雅地结束 `rx` 的循环。
- **异步等待**：使用 `.await` 确保不阻塞底层的物理线程。

# tokio::select!

在 C++ 中，如果你想同时等待多个事件（比如“数据到达”或“定时器超时”），通常需要使用 `select`/`epoll` 系统调用，或者复杂的 `std::condition_variable` 逻辑。而在 Rust Tokio 中，这被简化为了一个优雅的宏。

给一个任务设置“截止日期”。

```
pub async fn with_timeout<F, T>(future: F, timeout_ms: u64) -> Option<T>
where
    F: Future<Output = T>,
{
    // 方法一：使用 tokio::select! (练习重点)
    tokio::select! {
        // 分支 1: 原始任务先完成了
        res = future => Some(res),
        // 分支 2: 睡眠时间先到了
        _ = sleep(Duration::from_millis(timeout_ms)) => None,
    }

    // 方法二：使用内置的快捷函数（生产环境推荐）
    // tokio::time::timeout(Duration::from_millis(timeout_ms), future).await.ok()
}
```

同时运行两个任务，谁先跑完就用谁的结果，并**取消**另一个。

```
pub async fn race<F1, F2, T>(f1: F1, f2: F2) -> T
where
    F1: Future<Output = T>,
    F2: Future<Output = T>,
{
    tokio::select! {
        res = f1 => res,
        res = f2 => res,
    }
}
```

在 C++ 中，如果你启动了两个线程去抢一个任务，其中一个赢了，你很难“优雅地”杀掉另一个线程（`pthread_cancel` 是噩梦）。

而在 Rust 的 `tokio::select!` 中：
- **谁赢了，谁被保留。**
- **谁输了，谁被立刻销毁 (Drop)。** 因为 Rust 的异步是基于**状态机**的，`select!` 只需要简单地停止对失败分支调用 `poll`，并将其状态机结构体丢弃。由于 RAII 机制，失败分支里打开的 Socket、文件或定时器都会在 `Drop` 时自动关闭。这种**自动取消**是 Rust 异步安全性的精髓。

`tokio::select!` 的语法是：`<模式> = <Future> => <处理逻辑>`。
- 它会轮询所有的 Future。
- 只要有一个返回 `Poll::Ready`，对应的处理逻辑就会执行。
- 它保证**一次只会执行一个分支**的代码。

如果两个分支同时准备好了（比如 `f1` 和 `f2` 都在同一时刻返回），`select!` 会默认**随机**选择一个。
- 这对应 C++ 中处理 `epoll` 事件时的公平性问题。
- 如果你想让第一个分支拥有绝对优先级，可以使用 `tokio::select! { biased; ... }`。
